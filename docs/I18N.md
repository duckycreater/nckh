# BMO Robot — Internationalization Plan (i18n)

> Single source of truth for how localization is structured across the
> full stack: frontend UI, backend error messages, transactional email,
> audit timeline. Read this before adding a new locale, key, or template.

---

## 1. Scope

| Layer                | Pack                          | Files                                             | Owner |
| -------------------- | ----------------------------- | ------------------------------------------------- | ----- |
| Frontend UI strings  | 8 locales (vi/en/zh/es/fr/ja/ko/id) | `src/locales/{locale}.json`                   | FE    |
| Backend errors       | 10 locales (the 8 + `ar`, `pt`)     | `server/locales/{locale}.json`              | BE    |
| Email templates      | 10 locales                          | `server/locales/{locale}.json` → `email.*` | BE    |
| RTL foundation       | All locales; auto-applied for `ar/he/fa/ur/yi` | `src/lib/rtl.css`                  | FE    |

Adding **Arabic** is fully wired (CSS, route resolution, locale table,
backend email + errors). Adding it to the user-visible frontend language
switcher is a one-line change to `LANGUAGES` in `src/lib/i18n.ts` (the
fallback to English already works).

## 2. Frontend i18n

### 2.1 Stack
- [`react-i18next`](https://react.i18next.com/) with `partialBundledLanguages: true`
- Single import in `src/lib/i18n.ts` that bundles all 8 packs eagerly
- Persistent storage key: `bmo_language` (legacy `ecoquest_language` is
  read once at boot and migrated automatically)
- `<html dir>` is mutated by `applyDocumentDirection()` on every
  `languageChanged` event

### 2.2 Adding a string in code
```tsx
import { useTranslation } from "react-i18next";

function MyComp() {
  const { t } = useTranslation("namespace"); // optional, defaults to "common"
  return <button>{t("save", "Save")}</button>;
}
```

> Use the second argument as the inline English fallback. CI will warn if
> the key is missing in `en.json`.

### 2.3 Fallback chain
```
active_locale → "en" → "vi" → key
```
Configured via `i18n.init({ fallbackLng: ["en", "vi"] })`.

### 2.4 Adding a brand-new namespace
1. Add it under `src/locales/en.json` first.
2. Run `node scripts/inject-i18n-keys-2.cjs` (or copy-paste the new
   branch into the other packs).
3. Ensure `src/lib/i18n.ts` imports it (already does for the 8 packs).
4. Run `node scripts/check-i18n.cjs` to confirm parity.

## 3. Backend i18n

### 3.1 Locale detection (every request)

`server/services/localeRouter.ts` exposes `localeMiddleware` which
attaches `req.locale`:

```
x-bmo-locale        → user preference (highest priority)
Accept-Language     → RFC 4647 negotiation
x-vercel-ip-country → GeoIP
fallback            → "vi"
```

Mounted globally in `server/bootstrap.ts` so every route can pull
`req.locale.locale`.

### 3.2 Error messages

```ts
import { err } from "../services/errorMessages.js";

router.post("/clans", (req, res) => {
  if (!req.body.name) return err(res, 400, "error.clan.nameTooShort", req);
  // ...
});
```

Lookup order: `locales/<req.locale.locale>.json` → `locales/en.json` →
return the key (last-ditch, surfaces the bug instead of leaking an
English string).

### 3.3 Transactional email

```ts
import { renderEmailTemplate } from "../services/emailTemplates.js";

const { subject, html, text } = renderEmailTemplate("welcome", req.locale?.locale, { name: user.nickname });
await mailer.send(user.email, { subject, html, text });
```

Templates currently defined: `welcome`, `password_reset`,
`achievement`, `weekly_summary`. Add to `server/locales/*.json` →
`email.<template>.{subject,body}` then re-run `node scripts/check-server-locales.cjs`.

### 3.4 Audit timeline

`GET /api/audit/timeline` returns `{events, cursor, locale}`. The
frontend (`AuditTimeline.tsx`) sends the active locale via
`Accept-Language` + `x-bmo-locale`, and reloads the list whenever the
user changes language so the rendered descriptions stay in sync.

## 4. RTL foundation

| Item                   | Where                                  |
| ---------------------- | -------------------------------------- |
| `dir` attribute        | `<html dir="rtl\|ltr">` via `applyDocumentDirection()` |
| Arabic font cascade    | `src/lib/rtl.css` (`:root[dir="rtl"]`) |
| Physical → logical CSS | `src/lib/rtl.css` (`pl-4` → `padding-inline-start`) |
| Numeric inputs LTR     | `src/lib/rtl.css` (`.bmo-numeric`, `input[type=number]`) |
| Icon flip helper       | `data-flip-rtl="true"`                 |
| Smoke test             | `tests/lib/rtl.spec.ts`                |

Logical properties are supported in all evergreen browsers (~97% global
coverage, including every mobile browser shipped since 2022).

## 5. Adding a new locale

Full procedure (15 minutes if you only need UI; longer if you also need
backend error/email coverage):

1. **Add JSON file**
   - Frontend: `src/locales/xx.json` (copy `en.json` and translate)
   - Backend: `server/locales/xx.json`
2. **Register code**
   - `src/lib/i18n.ts` → `LANGUAGES` + import
   - `server/services/errorMessages.ts` → `LocaleCode` + `SERVER_SUPPORTED_LOCALES`
3. **Add to GeoIP map**
   - `server/services/localeRouter.ts` → `COUNTRY_TO_LOCALE` (optional)
4. **Run**
   - `node scripts/check-server-locales.cjs` (parity)
   - `node scripts/check-i18n.cjs` (master guard)
5. **Manual**
   - Open Settings → Language switcher → pick the new code
   - Toggle RTL on/off (if locale is RTL) → confirm layout mirrors
   - Test sign-in, clan creation, email signup

## 6. CI guard

`scripts/check-i18n.cjs` runs in CI on every PR. It fails the build if:

- Any `*.json` locale file has duplicate keys
- Any backend locale file is missing required ErrorKey coverage
- A locale is missing **>30%** of `en.json`'s keys (smaller gaps are
  logged as warnings because i18n's `fallbackLng` chain handles them at
  runtime)

Wire into your CI of choice:

```yaml
# .github/workflows/ci.yml (excerpt)
- name: i18n guard
  run: node scripts/check-i18n.cjs
```

## 8. ADR-0006: Right-to-left support foundation

> Decision: ship RTL CSS, `dir` switching, and Arabic-in-server pipeline
> in this release; defer adding `ar` to the user-visible language
> switcher until a content partner confirms Arabic translations are
> acceptable quality.

- Pro: every UI component already mirrors automatically; flipping a flag
  at deploy time is one line of code.
- Con: a small fraction of components rely on physical properties and
  visual flips; the `rtl.css` overrides cover the common cases but a few
  bespoke placements still need manual review. Tracked under
  `// TODO(rtl)` in future PRs.

## 9. Testing checklist (manual)

```bash
# 1. Boot dev server with full i18n stack
node scripts/check-i18n.cjs
npm test -- tests/lib/rtl.spec.ts
node --experimental-strip-types scripts/smoke-i18n.ts

# 2. Toggle each locale, check:
#    - Language switcher label updates
#    - <html lang>/<html dir> attribute updates
#    - Profile name displays correctly (no tofu boxes)
#    - Numbers/dates use locale separators

# 3. Force Arabic manually:
#    localStorage.setItem("bmo_language", "ar")
#    → confirm dir=rtl, font switches, layout mirrors
#    → confirm chat, audit timeline, leaderboard all read right-to-left

# 4. Backend:
#    curl -H "Accept-Language: ja" /api/audit/timeline | jq .locale
#    → expect "ja"
```
